**Date:** 2026-05-13  
**Status:** Approved

## Overview

This addendum extends the dev-workflow plugin with three additions:

1. **`init-design-system` skill** — guided selection of component library and color palette, generates `docs/design-system.html` and `.claude/rules/ui.md` with resolved tokens
2. **`docs/icons.html`** — visual icon catalog generated alongside the design system, with a lightweight `/update-icons` command to keep it current
3. **i18n as mandatory** — `rules/ui/i18n.md` standard, i18n scaffold in `locales/`, and `i18n-compliance` skill wired into `quality-review`

---

## 1. `init-design-system` Skill

### Purpose

Generates the complete visual identity of a project. Callable from `init-project` and standalone to update an existing project's design system at any time.

### Standalone command

```
/init-design-system
```

Reads the existing `docs/plan.md` for product context if present. Can be run after the initial `init-project` to refresh the design system.

### Flow

```
1. Read docs/plan.md → extract product type, target users, tone
2. Present component library options (with description + example link + included icon set)
3. User selects library
4. Propose 3 contextualised color palettes based on product context
5. User selects palette or describes custom colors
6. Generate docs/design-system.html
7. Generate docs/icons.html  (see Section 2)
8. Write .claude/rules/ui.md (resolved tokens + contrast rules)
```

### Component library options presented

| Option | Style | Included icons | Link |
|--------|-------|----------------|------|
| shadcn/ui | Minimalist, headless, Radix-based | Lucide | shadcn.com |
| DaisyUI | Themed, Tailwind-native | Heroicons | daisyui.com |
| Mantine | Full-featured, accessible, with hooks | Tabler Icons | mantine.dev |
| Flowbite | Bootstrap-style, Tailwind | Flowbite Icons | flowbite.com |
| None (CSS vars) | Raw design tokens only | User's choice | — |

### Color palette proposal

Three palettes are generated contextually. Each palette contains:
- `primary` — main brand color (with 50–950 scale)
- `surface` — page and panel backgrounds (light / dark values)
- `accent` — secondary action color
- Resolved contrast ratios for primary text on each surface (WCAG AA check)

Example for a sports management app:

```
Paleta A "Campo de juego"
  primary:  #16A34A (green-600)  contrast on white: 4.6:1 ✅
  surface:  #F0FDF4 / #052E16
  accent:   #FACC15 (yellow-400)

Paleta B "Equipación"
  primary:  #2563EB (blue-600)   contrast on white: 5.9:1 ✅
  surface:  #EFF6FF / #1E3A5F
  accent:   #F97316 (orange-500)

Paleta C "Noche"
  primary:  #7C3AED (violet-600) contrast on white: 5.5:1 ✅
  surface:  #F5F3FF / #1E1B4B
  accent:   #06B6D4 (cyan-500)
```

### `docs/design-system.html`

Standalone HTML file (no server required). Contains:
- CSS variable declarations for all tokens
- Color palette swatches with hex values and token names
- Typography scale (size, weight, line-height)
- Spacing scale
- Representative components from the chosen library: buttons (all variants), cards, badges, inputs, navigation, status indicators
- WCAG contrast table calculated from the project's actual token values
- Dark mode toggle if the project supports dark mode

### `.claude/rules/ui.md`

Fills the `rules/templates/ui-design-tokens.md` template with resolved values for this project. Format mirrors the existing `ui-contrast.md` from team-manager:

```markdown
# UI Design Tokens — [Project Name]

## Component library: [chosen library]

## Token Reference (Light / Dark)
| Token | Light | Dark |
|-------|-------|------|
| bg-page    | #... | #... |
| bg-panel   | #... | #... |
| text-strong| #... | #... |
| ...        |      |      |

## Contrast Catalogue
[WCAG ratios for all common text/background combinations]

## Pattern Catalogue
[Correct and incorrect usage patterns for this project's tokens]
```

This file is the single source of truth read by `ui-contrast`, `quality-review`, `update-mockups`, and the code quality checklist.

### Updated `init-project` flow

```
1. check-dependencies(framework)
2. init-brainstorm          ← functional design (features, architecture)
   GATE: developer approves high-level design
3. init-scaffold            ← directory structure + CLAUDE.md + i18n scaffold
4. init-design-system       ← library selection + palette + design-system.html
5. write-plan
6. init-generate-specs
```

## 2. Icon Library (`docs/icons.html`)

### Generated by `init-design-system`

Created in step 4 of `init-project`, immediately after the component library is chosen. The icon set used corresponds to the library's default icon package (see table above).

### File content

Standalone HTML (no server, no build step). Contains:

- **Header**: project name + icon library name + version
- **Search bar**: filters icons by name (inline JS, no dependencies)
- **Size selector**: 16 / 24 / 32 px
- **Color selector**: primary / text-strong / text-soft / custom hex
- **Icon grid** grouped by category:
  - Navigation (home, back, forward, menu, close, chevrons...)
  - Actions (add, edit, delete, save, upload, download, copy...)
  - Status (check, error, warning, info, loading, pending...)
  - Communication (mail, chat, notification, bell, share...)
  - Data (chart, table, filter, sort, search, refresh...)
  - Domain-specific (icons added manually for this project)

Each icon shows: visual preview + icon name + copy-ready usage snippet for the project's stack.

Example snippet (shadcn/Lucide):
```tsx
import { Home } from "lucide-react"
<Home size={24} className="text-primary" />
```

### Keeping the catalog current

When a `dev-cycle` introduces icons not present in `docs/icons.html`, the `update-mockups` skill appends a notice at the end of the cycle:

```
⚠ Uncatalogued icons detected: Trophy, Shield
  → Run /update-icons to add them to docs/icons.html
```

### `/update-icons` command

A lightweight command that invokes the `update-icons` skill. The skill:
1. Reads the current `docs/icons.html`
2. Scans changed files in the branch for icon imports not in the catalog
3. Adds the new icons to the appropriate category in `docs/icons.html`
4. Does not re-run the full design system generation

```
/update-icons          ← scans branch for new icons, updates docs/icons.html
/init-design-system    ← full regeneration (library change, palette update)
```

### CLAUDE.md reference

`init-scaffold` adds to the project's CLAUDE.md index:

```markdown
## Documentation
- Design system: [docs/design-system.html]
- Icon catalog:  [docs/icons.html]
...
```

## 3. Mandatory Internationalisation

### `rules/ui/i18n.md`

Canonical rule applied to all projects built with this framework. Skills read this file; it is not project-specific.

**Rules:**

- **No hardcoded user-visible strings** in source code. Every text string belongs in a translation file under `locales/`.
- **Dates, times, and numbers** must use `Intl.DateTimeFormat` / `Intl.NumberFormat` or the equivalent API of the chosen i18n library. Never string concatenation with locale assumptions.
- **Plurals and grammatical gender** use the library's plural utilities. Never inline ternary: `n === 1 ? "item" : "items"`.
- **The default locale** is defined during `init-project` and read from config at runtime. Code never assumes a fixed locale.
- **Key naming convention**: `namespace.feature.element` — e.g. `polls.status.open`, `common.actions.save`, `errors.notFound`.
- **Namespace per feature**: each major feature area has its own translation file. Shared strings go in `common`.

**Accepted exceptions:**
- Log messages and error strings that only appear in server console output
- Code identifiers, enum values, URL slugs
- Dates/numbers in non-user-visible contexts (internal computations, API request params)

### `init-brainstorm` addition

After the functional brainstorming session completes (features, architecture, stack), `init-brainstorm` asks two technical setup questions before closing:

1. **i18n library**: next-intl (Next.js), i18next, react-i18next, LinguiJS, or none
2. **Project languages**: default locale + additional locales to support

These answers are recorded in `docs/plan.md` under a `## Technical Setup` section and consumed by `init-scaffold`.

### What `init-scaffold` creates

```
locales/
  [default-locale]/
    common.json       ← shared strings: actions, errors, dates, navigation
    [feature-1].json  ← one file per feature from brainstorm output
    [feature-2].json
    ...
  [additional-locale]/
    common.json
    [feature-1].json
    ...
```

Each JSON file is pre-populated with placeholder keys derived from the feature names in `docs/plan.md`, so the developer has a starting structure rather than blank files.

Example `locales/es/common.json` stub:
```json
{
  "actions": {
    "save": "Guardar",
    "cancel": "Cancelar",
    "delete": "Eliminar",
    "edit": "Editar"
  },
  "errors": {
    "generic": "Ha ocurrido un error",
    "notFound": "No encontrado",
    "unauthorized": "Sin permisos"
  }
}
```

The project's CLAUDE.md index gets an i18n section:

```markdown
## i18n
- Library: [chosen library]
- Default locale: [es|en|...]
- Additional locales: [list]
- Translation files: [locales/]
- Standard: [.claude/rules/ui/i18n.md]
```

### `i18n-compliance` Skill

Invoked automatically by `quality-review` after every implementation cycle. Scans files modified in the current branch.

**Detects:**

| Violation | Severity | Example |
|-----------|----------|---------|
| Hardcoded user-visible string | HIGH | `"Guardar cambios"` in JSX |
| Hardcoded locale in Intl API | HIGH | `toLocaleDateString('es-ES')` |
| Inline plural ternary | MEDIUM | `` `${n} item${n===1?'':'s'}` `` |
| Missing translation key (key used in code but absent in locales/) | HIGH | `t('polls.newKey')` not in any JSON |
| Locale assumed in date arithmetic | LOW | `new Date().toLocaleDateString()` without locale param |

**Output format** (mirrors `security-review-code`):

```
[i18n] PASS

or

[i18n] VIOLATIONS FOUND

  [HIGH] src/components/poll-card.tsx:34
  Hardcoded string: "Encuesta abierta"
  → Move to locales/es/polls.json: polls.status.open

  [MEDIUM] src/components/squad-list.tsx:67
  Inline plural: `${count} jugador${count === 1 ? '' : 'es'}`
  → Use: t('squad.players', { count })
```

Any `HIGH` violation blocks the PR (same gate as `security-review-code`). `MEDIUM` and `LOW` are presented to the developer who decides whether to fix before merge.
